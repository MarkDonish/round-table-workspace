## 主贴

Codex / Claude Code 写完一段功能，你敢直接 merge 吗？

我每次都不敢。AI 输出太自信了，看起来都对，但鬼知道哪里埋了坑。

所以我做了一个本地工具，叫 Round Table Workspace。

用法很简单：把 AI 的产出丢进去，系统自动拉几个不同视角的子代理，开一场圆桌会议，挨个挑毛病、补证据、找风险。最后给你三个字：ship / revise / reject。

没有 API key 也能跑。本地优先，GitHub 开源。

👇 往下看怎么用

GitHub: https://github.com/MarkDonish/round-table-workspace
Demo: https://markdonish.github.io/round-table-workspace/

## 回复 1

先说场景。

你用 Codex 或 Claude Code 写了一坨代码，AI 跟你说"这个功能完成了"。你看着 diff，感觉还行，但又不太确定——

- 边界情况测了吗？
- 用户会买账吗？
- 有没有偷偷引入安全风险？
- 宣传文案里写的能力，真的验证过了吗？

这时候你只有两个选择：信它，merge；或者自己花半小时逐行 review。

Round Table Workspace 给你第三个选择：让一群 AI 角色替你吵一架。

---

## 回复 2

机制用大白话讲是这样的：

系统里有一批预设好的角色池——产品视角、工程视角、风险视角、用户视角、主持人。

你丢一个问题进去，比如"这个 AI 写的 onboarding 流程能不能上线？"，系统先判断这是工程类问题还是产品类问题，然后从角色池里筛出 3-5 个当前最有用的角色。

不是所有角色一起上，只选这次用得上的。

---

## 回复 3

选好的角色一个个进入圆桌，按自己的职责发言。

工程角色会讲：代码结构合理吗？测试覆盖了吗？
产品角色会讲：这个功能切中用户痛点了吗？定位清晰吗？
风险角色会讲：有什么会翻车的地方？假设稳不稳？
用户视角会讲：普通用户第一眼看懂吗？会不会困惑？

每个角色必须给理由、挑毛病、指出缺失的验证证据。不能只说"我觉得可以"。

---

## 回复 4

主持人最后汇总。

输出不是一篇长篇大论，是结构化的结论：

- 共识是什么
- 分歧在哪里
- 哪些风险还没排除
- 缺什么证据
- 下一步该做什么
- 最终判断：ship / revise / reject

举个例子：

```text
Decision: revise
Panel: product, engineering, risk, user-advocate
Why: 方向有用，但对外宣称的能力还没跑过 live 验证
Next: 补测试，加可见 demo，没验证过的能力先别写进文案
```

## 回复 5

几个实际能用上的场景：

- AI 写完功能要 merge，ship-check 跑一遍
- 有个产品想法，不确定值不值得做，开个 /room 先探索
- 方向定了但风险大，开个 /debate 正式审一轮
- README 或宣传文案写完了，丢进去让多个角色挑刺
- 团队里有人习惯性相信 AI 输出，用这个当决策 gate

三条命令：

```bash
./rtw ship-check "这个 AI 写的功能能上线吗"
./rtw room "最小可验证的 MVP 切口在哪"
./rtw debate "这个方向值不值得做"
```

## 为什么这样写

1. **开头直接，场景先行**——第一句话就是用户每天面对的真实问题，不是先介绍工具再讲场景。读者在 3 秒内能判断"这跟我有关"。

2. **机制用对话讲，不写成文档**——角色筛选、上桌讨论、主持人决策，全部用"你丢一个问题进去→系统判断→筛角色→角色说话→主持人汇总"这个自然流程串下来，读起来像在听一个人解释，不像在翻 README。

3. **故意拆成多个短回复**——X 上 thread 的阅读节奏和文章完全不同。每条回复只讲一个点，刷到就能看懂，不用回头翻上下文。这也符合"短句、口语化"的要求。

4. **有具体输出示例**——ship-check 那段 JSON 风格的输出直接贴出来，比一百句"它会给出结构化结论"都有说服力。读者看到"Decision: revise"就知道这东西不是在画饼。

5. **最后一条主动示弱**——"不吹不编：没有几万 star，没有生产案例"。开源社区最讨厌夸大宣传，先自曝短板反而真实。目标读者是程序员，程序员吃这套。

6. **禁用词全部避开**——全文没有"赋能""革命性""范式转移""重新定义""不是……而是……""在当今快速发展的 AI 时代"。对比用场景化方式表达——比如"这时候你只有两个选择……这个工具给你第三个选择"，比"不是……而是……"自然得多。

7. **回复 5 把命令直接贴出来**——程序员看到 bash 命令就会想"能不能跑"，这比任何文案都有转化力。
